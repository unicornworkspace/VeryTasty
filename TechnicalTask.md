# ТЗ: Digital-платформа ресторана «Особо Вкусно»

**Версия:** 1.1 · 07.10.2026
**Изменение относительно v1.0:** backend переведён с NestJS на Django + Django REST Framework, фоновые задачи — Celery + Redis. Остальные принципы сохранены.

---

## Главный принцип проекта

Не строим три независимых продукта. Сначала создаём единое серверное ядро и веб-платформу. Затем подключаем к тому же API iOS и Android. Будущая оплата, касса, доставка и ИИ добавляются как новые модули, а не как переписывание системы.

**Web, iOS и Android — это три интерфейса одного продукта.** Меню, гости, акции, loyalty и заказы не должны иметь по три версии бизнес-логики. Бизнес-правила принадлежат backend; интерфейсы только отображают и вызывают их.

## 1. Что мы строим

Система для ресторана «Особо Вкусно» состоит из единого backend и нескольких интерфейсов. Гость может пользоваться сайтом или мобильным приложением. Владелец и сотрудники работают через защищённую веб-панель. Все основные данные хранятся в одном месте.

| Компонент | Роль в системе | Что делаем на старте |
|---|---|---|
| Сайт | Клиентский интерфейс без установки | Меню, карта гостя, акции, аккаунт, заявки |
| iOS | Мобильный интерфейс | Тот же функционал API в нативной мобильной оболочке |
| Android | Мобильный интерфейс | Тот же функционал API |
| Admin | Интерфейс владельца | Меню, цены, фото, акции, промокоды, гости, лояльность, заявки |
| Staff | Рабочее место персонала | Заявки, QR гостя, подтверждение бонусных операций |
| Backend/API | Центральное ядро | Авторизация, меню, гости, loyalty, акции, заявки, уведомления |
| PostgreSQL | Основная база | Хранит бизнес-данные и историю операций |
| Redis | Брокер и кэш | Очередь Celery, кэш, rate limit |
| Celery | Фоновые задачи | Outbox, push, SMS, повторные попытки |
| Интеграции | Внешние сервисы | Telegram/MAX сейчас; POS/payment/delivery/AI позже |

## 2. Что уже есть у ресторана и что берём в основу

По присланным материалам текущая система на QR-Cafe уже умеет работать с меню, категориями, фотографиями, описаниями, весом/объёмом, ценами, скидками и стоп-листом. Есть настройки внешнего вида, рекламные слайдеры, QR-меню для столов, базовые способы получения/оплаты, расписание, интеграции меню для Яндекс/2ГИС, Яндекс.Метрика и уведомления заявок через Telegram/MAX. Владелец хочет заменить арендуемую платформу собственной системой.

**Что не переносим механически.** Мы не копируем интерфейс QR-Cafe один в один. Сохраняем полезную бизнес-логику, но делаем новую структуру и дизайн. При переносе проверяем, какие данные реально можно выгрузить из текущего сервиса: меню, фотографии, цены, категории, SEO и прочее.

## 3. Технологический стек

| Mobile | React Native + Expo | Одна кодовая база для iOS и Android, но отдельные сборки и публикации. |
| Backend | Django + Django REST Framework | Зрелый фреймворк, встроенная админка, ORM, миграции, аутентификация, permissions, signals. Много готовых решений — меньше кода писать с нуля. |
| Язык backend | Python 3.12+ | Стабильный, поддерживаемый, совместим с Django 5.x. |

| API-схема | drf-spectacular | Автогенерация OpenAPI 3.1 из DRF-вьюх и сериализаторов. |
| Валидация | DRF Serializers + pydantic v2 (для внешних payload'ов) | Сериализаторы — на границе API, pydantic — для вебхуков и внутренних структур. |
| Фоновые задачи | Celery | Outbox, push, SMS, повторные попытки, периодические задачи. |
| Брокер и кэш | Redis | Брокер Celery + кэш + rate limit. |
| Периодические задачи | Celery Beat | Напоминания, reconciliation, cleanup. |
| Data fetching (web/mobile) | TanStack Query | Кэширование и синхронизация данных без ручного управления состоянием. |
| Styling | CSS/Tailwind для web; design tokens для mobile | Единые цвета, типографика, отступы и состояния. |
| API | REST + OpenAPI 3.1 | Простой понятный контракт между интерфейсами и backend. |
| QR | `qrcode` + short-lived signed token (itsdangerous / PyJWT) | Без хранения телефона/баланса внутри QR. |
| Push | APNs + FCM через Expo Notifications на пилоте | Один поток уведомлений для iOS/Android; позже можно перейти на прямые APNs/FCM. |
| SMS | Абстракция `SmsProvider`; пилот: SMS.ru или MTS Exolve | Меняем провайдера без переписывания авторизации. |
| Monitoring | Sentry (sentry-sdk) + server uptime monitor | Ошибки и падения видны разработчику. |
| Analytics | Яндекс.Метрика для web + собственные продуктовые события | Не нужен отдельный дорогой CDP на пилоте. |
| Hosting | Timeweb Cloud, регион РФ | Простой старт для одного проекта; можно масштабировать позже. |
| Storage | S3-совместимое объектное хранилище | Фото и файлы не храним внутри PostgreSQL. |
| DevOps | Docker Compose + Caddy/Nginx | Минимальная инфраструктура для начинающего разработчика; без Kubernetes. |
| ASGI/WSGI | Gunicorn + Uvicorn workers (или Daphne при необходимости WebSocket) | Стандартный production-запуск Django. |
| Тесты | pytest + pytest-django + factory_boy | Гибче и быстрее, чем встроенный Django test runner. |
| Логирование | structlog | Структурные логи без PII, удобно парсить. |
| Конфиг | django-environ + `.env` | 12-factor, секреты не в коде. |

### Почему Django, а не FastAPI

- Встроенная админка Django — быстрый способ дать владельцу доступ к данным на время разработки (не отменяет отдельную admin-панель на Next.js, но не блокирует).
- Django ORM + миграции + auth + permissions + signals + Celery integration — из коробки. Меньше инфраструктурного кода.
- DRF — зрелый, документированный, с готовыми ViewSet, permissions, throttling, pagination.
- drf-spectacular даёт OpenAPI 3.1, из которого генерируется TS-клиент для web/mobile.
- Для одного ресторана и 10 000 гостей производительности Django более чем достаточно.

### Почему не микросервисы

На масштабе одного ресторана и до 10 000 зарегистрированных гостей отдельные микросервисы добавят сложность, но не дадут соразмерной пользы. Начинаем с модульного монолита Django: приложения (`apps`) изолированы по доменам, но живут в одном процессе. Границы приложений проектируем так, чтобы при росте отдельный модуль можно было вынести в сервис позже.

## 4. Общая архитектура

Главный принцип: интерфейсы не ходят напрямую в PostgreSQL и не знают секреты интеграций. Все изменения проходят через backend.

```
WEB (сайт + admin + staff)      MOBILE (iOS/Android)
        \                       /
         \   REST API + OpenAPI /
          \                   /
           +---- Django + DRF ----+
           |                      |
           |  apps: auth, users,  |
           |  menu, promotions,   |
           |  loyalty, requests,  |
           |  notifications,      |
           |  admin, audit,       |
           |  integrations,       |
           |  analytics           |
           +----------+-----------+
                      |
        +-------------+-------------+
        |                           |
   PostgreSQL                   Redis (broker/cache)
        |                           |
        |                     Celery workers + Beat
        |                           |
        |              +------------+------------+
        |              |            |            |
        |         Telegram/MAX   Push (FCM)   SMS (OTP)
        |
     S3 storage (media, backups)
```

| Django app | Ответственность |
|---|---|
| `auth` | OTP, access/refresh tokens, сессии, устройства |
| `users` | Профиль гостя, согласия, адреса в будущем |
| `menu` | Категории, блюда, модификаторы, цены, стоп-лист |
| `promotions` | Акции, промокоды, период, аудитория, условия |
| `loyalty` | Баланс и неизменяемый журнал операций |
| `orders` (`requests`) | Корзина, заявка/заказ, позиции, статусы; на пилоте оплата offline |
| `notifications` | Push, Telegram/MAX, повторные попытки |
| `admin` | Роли, права, настройка контента |
| `audit` | Кто и когда изменил данные/провёл бонусную операцию |
| `integrations` | POS/payment/delivery/AI adapters; на пилоте пустые интерфейсы |
| `analytics` | Продуктовые события и ключевые показатели |

- Чтение — в `selectors.py`, запись — в `services.py`.
- Интерфейс общается с API через типизированный клиент.
- Бизнес-правила не помещать в React-компоненты.

## 7. Часть I — Пилот. Web-платформа

Работаем сначала только с web: backend + сайт + admin + staff. Цель — получить полностью демонстрируемый и частично рабочий продукт до начала мобильной разработки.

### 7.1. Шаг 1: создать каркас backend

- Создать Django-проект (`django-admin startproject config .`).
- Разделить настройки: `base.py`, `local.py`, `staging.py`, `production.py`.
- Подключить `django-environ` и `.env`.
- Подключить PostgreSQL (`psycopg[binary]`).
- Подключить DRF, drf-spectacular, django-cors-headers, django-filter.
- Подключить Celery + Redis, создать `config/celery.py`.
- Сделать `/health` endpoint (проверка БД + Redis).
- Настроить глобальный exception handler для DRF.
- Добавить Swagger/OpenAPI через drf-spectacular (`/api/schema/`, `/api/docs/`).
- Добавить структурированное логирование (structlog) без персональных данных.
- Сделать `Dockerfile` и `docker-compose` для local development (web, postgres, redis, celery worker, celery beat).

### 7.2. Шаг 2: создать базовую структуру БД

| Таблица/сущность | Минимальные поля |
|---|---|
| `users` | id, phone, name, status, marketing_consent, created_at, updated_at |
| `staff_users` | id, login, password_hash, role, status |
| `categories` | id, name, slug, image, sort_order, is_active |
| `menu_items` | id, name, slug, description, image_url, unit, quantity, price, is_active, stop_list, created_at, updated_at |
| `menu_item_categories` | menu_item_id, category_id |
| `promotions` | id, title, description, image_url, start_at, end_at, status, audience_type |
| `promo_codes` | id, code, promotion_id, max_uses, used_count, expires_at |
| `loyalty_accounts` | user_id, balance_cached, status |
| `loyalty_transactions` | id, user_id, type, amount, reference_type, reference_id, idempotency_key, created_by, created_at |
| `requests` | id, user_id, status, total_preview, comment, channel, created_at |
| `request_items` | request_id, menu_item_id, name_snapshot, price_snapshot, qty |
| `devices` | id, user_id, platform, push_token, enabled, updated_at |
| `outbox_events` | id, type, aggregate_id, payload_json, status, attempts, next_attempt_at |

**Правила:**
- `loyalty_transactions` — неизменяемый журнал. Никаких UPDATE/DELETE. Только INSERT.
- `balance_cached` в `loyalty_accounts` — денормализация для быстрого чтения. Восстанавливается из журнала.
- `idempotency_key` — уникальный индекс, защита от дублей.
- `outbox_events` — паттерн outbox для надёжной доставки уведомлений.

### 7.3. Шаг 3: авторизация гостя

- `POST /auth/request-otp` → сервер ограничивает частоту запросов и создаёт OTP-сессию.
- `POST /auth/verify-otp` → проверка OTP → создаётся/находится пользователь → выдаются access/refresh tokens.
- `GET /me` → текущий профиль.
- `POST /auth/refresh` → обновить access token.
- `POST /auth/logout` → отозвать текущую refresh-сессию.
- Не хранить OTP и пароли в открытом виде. В логах не хранить OTP, токены и полные номера телефона.

**Реализация:**
- OTP — `django.core.signing` или PyJWT с коротким TTL, хранение хеша в Redis.
- Access token — JWT, TTL 15 минут.
- Refresh token — opaque, хранится в БД, rotation при каждом использовании.
- Rate limit — `django-ratelimit` или собственный на Redis.
- SMS — через `SmsProvider` adapter (SMS.ru или MTS Exolve).
- Отправка SMS — через Celery-задачу, не блокирует HTTP-ответ.

### 7.6. Шаг 6: QR карты гостя

- На экране карты генерировать краткоживущий подписанный токен (TTL 30–60 секунд).
- Не помещать внутрь QR телефон, баланс или другие персональные данные.
- Сотрудник сканирует QR камерой телефона/планшета или вводит одноразовый код вручную.
- Backend проверяет подпись, срок действия и статус гостя.
- Для начисления/списания сотрудник подтверждает операцию и связывает её с идентификатором чека.
- После подтверждения гость видит обновлённый баланс и запись в истории.

**Реализация:**
- Токен — PyJWT с коротким TTL, подпись секретом сервера.
- Внутри токена — только `user_id` и `nonce`.
- Проверка — на стороне Django, в `loyalty/services.py`.
- Защита от повтора — `idempotency_key` в `loyalty_transactions`.

### 7.7. Шаг 7: заявки без онлайн-оплаты

На пилоте это не полноценный интернет-заказ с оплатой, а контролируемая заявка.

```
Гость → корзина → «Отправить заявку» → request NEW
   ↓
Admin/Staff получает заявку
   ↓
Telegram/MAX уведомление (через Celery + outbox)
   ↓
сотрудник подтверждает
   ↓
ресторан готовит/выдаёт
```

**Реализация:**
- Заявка сохраняется в БД до отправки уведомления.
- Уведомление — через `outbox_events` + Celery-задачу.
- Если Telegram/MAX недоступен — задача повторяется с backoff.
- Статусы заявки: `NEW → CONFIRMED → PREPARING → READY → COMPLETED / CANCELLED`.

### 7.8. Шаг 8: акции и промокоды

- Создать простую модель: название, описание, изображение, период, тип аудитории.
- На пилоте поддержать 3 механики: процентная скидка, фиксированная скидка, промокод.
- Сохранять правила акции отдельно от рекламного текста.
- В админке показывать предпросмотр.
- Push отправлять только тем, кто дал маркетинговое согласие.
- Ограничить частоту массовых push, чтобы не раздражать гостей.

### 7.9. Definition of Done для Web-пилота

- Публичный сайт открывается по собственному домену через HTTPS.
- Меню можно полностью редактировать в панели без правки кода.
- Изменение блюда в панели появляется на сайте.
- Гость может зарегистрироваться по OTP.
- Карта показывает баланс и QR.
- Сотрудник может проверить QR и провести одну loyalty-операцию с защитой от повтора.
- Акция создаётся в панели и появляется на сайте.
- Гость может собрать заявку и отправить её.
- Заявка сохраняется в БД даже при недоступности Telegram/MAX.
- Сотрудник получает заявку в панели; мессенджер используется как уведомление.
- Работают логи, резервные копии и базовый мониторинг.

## 11. Часть III — Финальная докрутка и развитие

После того как базовая система стабильна, начинаем подключать автоматизацию. Порядок снова сохраняем: сначала сервер/веб, затем iOS, затем Android.

### 11.1. Web: доставка и интеграции

- Создать `DeliveryProvider` interface.
- Сначала реализовать одного поставщика доставки.
- Адрес → геокодирование → проверка зоны → стоимость → ETA.
- Заказ передаётся в POS/KDS через отдельный `POS adapter`.
- Кухня меняет статус, backend синхронизирует клиент.
- Курьерская система возвращает статусы.
- Ошибки внешних систем попадают в очередь на повтор или в ручной разбор.
- Поддержать собственных курьеров через простой mobile web staff interface прежде чем писать отдельное курьерское приложение.

### 11.2. Web: AI-помощник

- Сначала режим «помощник сотруднику»: AI предлагает ответ, человек отправляет.
- Создать отдельный `AiProvider` interface.
- AI получает актуальные данные только через разрешённые tools: `menu.search`, `promotion.list`, `order.status`, `faq.search`.
- AI не меняет баланс, не отменяет оплату и не обещает аллергенную безопасность без подтверждённых данных.
- Сложный вопрос → передача человеку.
- Сохранять диалог и оценку ответа только в пределах согласованной политики хранения данных.

### 11.3. iOS: финальные функции

- Статус заказа в реальном времени.
- Оплата и история заказов.
- Адреса доставки.
- Персональные предложения.
- QR заказа за столом в будущем.

## 13. Минимальная экономика инфраструктуры для пилота

Для пилота не нужен тяжёлый кластер. Основной принцип — оплачивать реальные ресурсы, а не технологический статус.

| Статья | Пилотный подход | Ориентир |
|---|---|---|
| Cloud server | 1 VPS/Cloud server, 4 vCPU / 8 GB RAM | Проверить текущий тариф провайдера |
| PostgreSQL | Managed DB или отдельная DB на том же провайдере | Для пилота можно начать с минимального managed-конфига |
| Redis | Managed Redis или контейнер на том же сервере | Небольшой инстанс достаточен |
| S3 | 10–100 GB для фото/файлов + отдельный bucket backup | Небольшая стоимость при малом объёме |
| SMS | По фактическому количеству OTP | Usage-based |
| Push | APNs/FCM | Обычно без отдельной платы за сам push-транспорт |
| Domain | Собственный домен | Оплата раз в год |
| Apple Developer | Аккаунт владельца | 99 USD/год |
| Google Play | Аккаунт владельца | 25 USD единоразово |
| RuStore | Аккаунт владельца | Проверить актуальные условия |
| Monitoring | Sentry + uptime | Начать с минимального тарифа |
| Delivery/payment | Не в пилоте | 0 ₽ до подключения, затем usage-based |

**Пример текущих цен инфраструктуры.** Timeweb Cloud на момент подготовки документа показывает Managed PostgreSQL, S3 и российские дата-центры; конкретная итоговая конфигурация должна быть выбрана по фактической нагрузке и требованиям к персональным данным. Эти значения не являются обещанной стоимостью всей инфраструктуры проекта.

## 15. Безопасность

| Риск | Что делаем |
|---|---|
| OTP abuse | Rate limit по IP + номеру + устройству; cooldown; блокировка подозрительных попыток |
| Потеря токена | Короткий access token, refresh rotation, logout/revoke |
| Loyalty fraud | Idempotency, audit, роли, привязка к операции/чеку, динамический QR |
| SQL injection | Django ORM/parameterized queries; никаких SQL из строки пользователя без параметров |
| XSS | Санитизация пользовательского HTML; контент из CMS не рендерить как raw HTML без причины |
| CSRF | Django CSRF для web-сессий; для API — token-based auth без cookies |
| Secret leak | `.gitignore`, secret store, ротация ключей |
| Backup failure | Ежедневные backup + ежемесячная контрольная проверка восстановления |
| Employee misuse | RBAC + audit log |
| PII leakage in monitoring | Нормализовать и маскировать телефон; не отправлять OTP/refresh tokens в Sentry |

## 21. Точный порядок разработки

Не перепрыгивать между всеми тремя приложениями. В любой момент должна существовать одна рабочая вертикаль.

- **Итерация 1:** репозиторий + Django skeleton + PostgreSQL + Redis + Celery + `/health`.
- **Итерация 2:** menu CRUD + public menu.
- **Итерация 3:** auth (OTP) + profile.
- **Итерация 4:** loyalty ledger + QR + staff scanning.
- **Итерация 5:** promotions + promo codes.
- **Итерация 6:** request flow + Telegram/MAX notification через Celery + outbox.
- **Итерация 7:** admin/staff polish + analytics + monitoring + backups.
- **Итерация 8:** web pilot demo and bug fixing.
- **Только после стабильности web:** iOS.
- **После стабильности iOS:** Android.
- **После пилота:** payment hardening, then payment integration.
- **После стабильной оплаты:** POS/delivery.
- **После достоверных данных:** AI.

**Золотое правило.** Каждая итерация должна заканчиваться работающим результатом. Не делать сначала 100% backend, потом 100% дизайн, потом 100% мобильное. Лучше каждые 1–2 недели доводить одну вертикаль от базы до экрана.

## 25. Критерии успеха первого этапа

- Ресторан владеет доменом, кодом и аккаунтами.
- Меню обновляется из панели и синхронно отображается на web/iOS/Android.
- Гость использует одну учётную запись на всех устройствах.
- Карта loyalty работает с журналом операций и защитой от дублей.
- Владелец может сам запустить акцию и промокод.
- Заявки не теряются при недоступности мессенджера.
- Персонал может работать с QR гостя без участия разработчика.
- Система имеет staging и production.
- Есть backup и проверенный restore.
- Есть мониторинг критических ошибок.
- Для второго этапа уже существуют точки подключения payment/POS/delivery, но они не включены случайно в пилот.

## 28. Финальная инструкция разработчику

Если разработчик только начинает, порядок действий должен быть буквально таким:

1. Прочитать этот документ целиком и сделать в README список задач.
2. Сделать репозиторий и поднять пустые `web` / `api` / `mobile`.
3. Проверить, что PostgreSQL и Redis поднимаются через Docker Compose.
4. Сделать Django-проект, разделить settings, подключить `django-environ`.
5. Сделать `/health` и убедиться, что API отвечает.
6. Подключить Celery + Redis, сделать тестовую задачу.
7. Сделать одну модель `Category` и вывести её на web.
8. Добавить `MenuItem` и вывести реальные блюда.
9. Добавить auth (OTP).
10. Добавить loyalty ledger.
11. Добавить QR.
12. Добавить staff scan + операция.
13. Добавить promotion.
14. Добавить request.
15. Добавить notification worker (Celery + outbox).
16. После рабочей web-версии начать mobile.
17. Не подключать оплату, POS, доставку и AI до стабильности предыдущего слоя.
18. Каждую новую функцию сначала описывать: пользовательский сценарий → данные → API → UI → тест → release.

## Главная архитектурная договорённость

Web, iOS и Android — это три интерфейса одного продукта. Меню, гости, акции, loyalty и заказы не должны иметь по три версии бизнес-логики. Бизнес-правила принадлежат backend; интерфейсы только отображают и вызывают их.

Backend — Django + DRF, фоновые задачи — Celery + Redis, БД — PostgreSQL, контракт — OpenAPI 3.1 через drf-spectacular. Фронт получает сгенерированный TS-клиент и не знает, на чём написан backend.
